# 0010 — iOS/iPadOS: a SwiftUI app over the Rust presenter, built without a Mac

- Status: accepted
- Date: 2026-10-24
- Plan: `docs/plans/2026-10-24-ios.md` (§2–§6; ROADMAP Wave 5)

## Context

dail should run on the user's iPad with the same engine, registry, keymap, palette flows and agent policy as the
desktop and Android, and with no rules in another language. ADR 0009 already gives a toolkit-free presenter
(`app-mobile`) that turns `AppState` into JSON frames and UI events into commands, and a host (`app-android`) that
holds the session behind six calls. That host mixes two parts: platform-neutral modules (`host.rs`, `calls.rs`,
`config.rs`, `outgoing.rs`, `error.rs`) and Android glue (JNI, Keystore, logcat).

There is no Mac. Xcode, Swift, linking against the Apple SDK, the simulator and signing are available only on GitHub's
`macos-latest` runners, which are free for public repositories. AGENTS.md §5 still forbids compiling C/C++. Linking
Apple system frameworks is allowed, as linking Windows system DLLs is.

## Decision

- **UI.** SwiftUI draws `app-mobile`'s frames and returns `UiEvent`s, as Compose does on Android. Swift does only what
  iOS can do: text input, VoiceOver, Keychain, files and lifecycle. egui on iOS (no IME composition), a WebView
  (hostile HTML would meet a browser engine) and UniFFI (a generator for six JSON calls) are rejected.
- **Crates.**
  - `app-host` ← app-core, app-io, app-sync, app-mobile (app-testkit behind its `demo` feature, as ADR 0001/0009
    allow). It takes the platform-neutral modules out of `app-android` as they are, with their tests. It uses the
    workspace lints unchanged (`unsafe_code = "forbid"`).
  - `app-android` ← app-host (+ the crates it already uses). It keeps only JNI, the Keystore store and logcat.
  - `app-ios` ← app-host. `crate-type = ["staticlib", "rlib"]`, `[lib] name = "dail"` (`libdail.a`). The six calls
    plus `dail_string_free` and `dail_bytes_free` are `extern "C"` functions in `src/ffi.rs`: UTF-8 C strings in,
    Rust-owned strings out (Swift frees them), blobs as `{ ptr, len }`, and the listener (alerts, wake) as a C
    function pointer plus a `void *` context. `include/dail.h` is hand-written, and a test matches it against the
    exports, so no `cbindgen` is needed. It builds and tests on every host; the iOS-only parts sit behind
    `cfg(target_os = "ios")`.
  - app-gui, app-tui, app-cli and app-mobile depend on none of them.
- **The lint exception** extends ADR 0009's to `app-ios`: the workspace table with `unsafe_code = "deny"`, and only
  `src/ffi.rs` has `#![allow(unsafe_code)]` with a `// reason:` line. A test pins the table, as app-android's does.
- **Secrets.** keyring 4 with Apple's native store, if it compiles no C (only `Security.framework` through
  `security-framework`) and passes `cargo deny`. Otherwise a small Swift Keychain bridge reached through the callback
  table. I1 records the choice.
- **Origin and agent channel.** The app is the user's front-end: `Origin::Gui`. There is no agent channel on iOS, for
  the reasons in ADR 0009. The palette reaches every command (a parity walk tests it).
- **Platform.** iOS/iPadOS 17 as the deployment target (the user's iPad runs 17 or newer), iPhone and iPad, arm64
  device and arm64 simulator. Bundle id `net.darii.dail`. The profile lives in Application Support, and Swift passes
  the path; nothing is read from the environment.
- **Project and CI without a Mac.** `ios/project.yml` is an XcodeGen spec. CI generates the Xcode project, which is
  never committed or edited by hand. `cargo xtask ios check` runs clippy `-D warnings` for `aarch64-apple-ios` and
  `aarch64-apple-ios-sim` on Linux, which is the local gate. `ios xcframework` and `ios app` need macOS and report
  "cannot run" elsewhere. `ci.yml` gets a path-filtered `ios` job on `macos-latest`, and `release.yml` an `ios` job
  that uploads unsigned IPAs (demo and live) with `.sha256`. `ios` is a non-default gate, like `android`.
- **Signing.** The first artifacts are unsigned. The user re-signs them with a free Apple ID (SideStore/AltStore or
  Sideloadly, Developer Mode on). A signed ad-hoc or TestFlight build waits for a paid account (plan §6).

## Consequences

- iOS reuses every rule and the JSON contract that Android already tests; Swift is a renderer and a platform adapter.
- The host split is a refactor with no behaviour change, and it lands before any iOS code, with the Android gate green.
- A second crate deviates from the workspace lints, confined to one file and pinned by a test.
- Swift and Xcode errors surface only in CI, after 10–20 minutes. The Swift surface stays small, and the frame
  fixtures are checked in Rust first.
- The repository must be public before the macOS jobs are useful (ROADMAP Wave 5 O).
