# Plan: dail on Android

- Status: proposal (2026-10-22). The items are ROADMAP Wave 4; ADR 0009, its first item, records §1–§4.
- Decided with the user on 2026-10-22:
  1. Kotlin and Jetpack Compose draw screen models that Rust computes (§1).
  2. The first release is a signed APK on GitHub releases. Google Play and F-Droid come later (§10).
  3. By default the app checks for mail in the background periodically. Push is opt-in (§4.4).
  4. After a review of the agent part: no agent channel on the phone in release builds (§4.7).
- Goal: a daily-drivable Android app. Phones come first; tablets, foldables and Chromebooks get two or three panes.
  It runs on the same engine, registry, keymap, palette flows and agent policy as the desktop, with no rules in Kotlin.
- Approach:
  - The session runs in the app's process, unchanged: `Session`, `LiveBackend`, redb, IMAP and SMTP, app-tls.
  - A new toolkit-free crate, `app-mobile`, turns `AppState` into screen models ("frames") and touch events into
    commands. It works the way `app-tui` turns the same state into a terminal buffer.
  - A thin Kotlin/Compose app draws the frames. It also does what only Android can: text input through any IME,
    TalkBack, notifications, background work, the Keystore, the file pickers and intents.
  - A new crate, `app-android`, connects the two through six JNI calls. They carry the JSON the command bus already
    speaks.
- Assumes the workspace as of UI-16 (`98326cc`).

## 1. Options considered

| Option | Verdict |
|---|---|
| egui/eframe on NativeActivity (all Rust, reuses app-gui) | No IME composition. winit 0.30's Android backend shows and hides the soft keyboard (`set_ime_allowed`), but its `set_ime_cursor_area` and `set_ime_purpose` are empty (`winit-0.30.13/src/platform_impl/android/mod.rs`). android-activity's NativeActivity backend returns an empty `text_input_state` and ignores `set_text_input_state` and `set_ime_editor_info` ("Unsupported"). Keys arrive one by one, so CJK input, swipe typing, autocorrect and voice typing don't work, and a mail client is mostly typing. The desktop widgets would need a touch rewrite anyway |
| egui on GameActivity | GameTextInput brings the IME, but android-activity's `game-activity` feature compiles GameActivity's C++ with `cc` (`android-activity-0.6.1/build.rs`). AGENTS.md §5 forbids that |
| Slint | A third toolkit; its royalty-free licence is not on `deny.toml`'s allowlist |
| Tauri 2, Dioxus mobile (a WebView) | Hostile HTML would be rendered by a browser engine, the attack surface dail avoids with its own document renderer (ARCHITECTURE §6). It would also mean a web UI next to two native ones |
| UniFFI + Compose | Typed Kotlin bindings, but its Kotlin backend loads the library through JNA. JNA ships a prebuilt C library (`libjnidispatch.so`) in every APK and does not call `JNI_OnLoad`. dail's commands, events and receipts are JSON already, so six hand-written calls are smaller than a generator |
| A thin client of a desktop `dail serve` | No mail without the desktop running. Declined on 2026-10-22 |
| **Compose over a Rust presenter, through JNI (chosen)** | The platform's own text input (any IME), TalkBack, Material components, RTL mirroring, notifications and background services. Every rule stays in Rust and is tested headless, like the TUI's. Costs: Kotlin and Gradle in the repository, and Android jobs in CI |

## 3. Scope

In scope (Wave 4):
- Android 10 (API 29) and newer, on arm64-v8a and x86_64 (emulators, Chromebooks). Phones, plus tablets, foldables and
  Chromebooks with two or three panes.
- The desktop's accounts and presets (password or app password), side by side.
- Read, triage (swipes, checked threads, undo and redo), search, compose, reply, forward, attachments in and out,
  drafts, and send with the undo window.
- Notifications, and background checks: periodic by default, push opt-in.
- Settings, account setup, the palette, hardware keyboards.
- A debug-only adb bridge, for tests and for agents that build and check the app (§4.7).
- A signed APK per ABI on GitHub releases.

Out of scope (later, §10):
- An agent channel on the phone (MCP, AppFunctions, an in-app agent), and approvals on the phone.
- Google Play and F-Droid.
- iOS.
- OAuth2, which comes with the desktop's item.
- PDF viewing and "open original"; widgets; Wear OS.
- At-rest encryption (SEC-1 in `docs/requests/2026-10-21.md`).
- 32-bit ARM.
- Google Play Services, Firebase/FCM and WorkManager.

## 4. Design

### 4.1 Crates and edges

```text
crates/app-mobile/    # touch front-end logic: frames (screen models), events → requests. No toolkit, no tokio, no JNI.
crates/app-android/   # the Android host, cdylib `libdail.so`: Host (session, bridge, presenter), JNI calls, Keystore, logcat.
android/              # the Gradle project: the Kotlin/Compose app. It draws frames and has no rules of its own.
```

Dependency rules (AGENTS.md §2, changed in A0):

```text
app-mobile  ← app-core, app-front, app-theme         (serde, schemars; no toolkit, no tokio, no JNI)
app-android ← app-core, app-io, app-sync, app-mobile  (jni, ndk-context, keyring's Android store on Android;
                                                       app-testkit behind the `demo` feature, as in ADR 0001)
```

- app-gui, app-tui and app-cli depend on neither crate. app-mobile can serve an iOS host later: SwiftUI over the same
  JSON (§10).
- app-android builds on every host.
  - The JNI glue compiles anywhere. The Android-only parts (the Keystore store, ndk-context, logcat) sit behind
    `cfg(target_os = "android")`.
  - So `cargo xtask verify` on Linux and Windows lints and tests it, and the JVM tests load the host build (§6).
- **The lint exception.** app-android is the only crate whose `[lints]` table is not `workspace = true`.
  - It is the workspace table with `unsafe_code = "deny"` instead of `forbid`.
  - Only `src/jni.rs` allows unsafe code: `#![allow(unsafe_code)]` with a `// reason:` line. JNI exports must not be
    mangled, and `JavaVM` and ndk-context take raw pointers.
  - A test compares the table with the workspace's, so the two differ only in that key.
- `[lib] name = "dail"`, `crate-type = ["cdylib", "rlib"]`.

Moves in A0, so that no front-end re-derives another's rules. Behaviour is unchanged, and the GUI's and TUI's tests stay
green.

| From | To | Why |
|---|---|---|
| `app_tui::text::{is_unsafe, clean, clean_lines}` | `app_front::text` | Compose draws bidi text faithfully, U+202E tricks included. Frames are sanitized like the TUI's buffer |
| `app_gui::list::row_name` and the sidebar's `"{label}, {n} unread"` | `app_front::a11y` | TalkBack reads the names that AccessKit reads |
| the pane choice in `app_tui::layout::arrange` | `app_front::panes` | One rule for which panes show at a width. The TUI keeps its `Rect`s |
| `app_gui::images::decode` (format sniffing, 4096 px, 96 MiB) | `app_io::images`, returning RGBA | The same limits for Android's previews. app-gui wraps the result in a `ColorImage` |

### 4.2 The presenter (`app-mobile`)

`Mobile` is UI-local state, like `Tui` and `Shell`. It reads `&AppState` and never changes it.

```rust
pub struct Mobile { /* clock, language, window class, list window, palette, composer buffers, folds, action table, … */ }

impl Mobile {
    pub fn frame(&mut self, state: &AppState) -> Frame;                         // the next screen
    pub fn event(&mut self, event: UiEvent, state: &AppState) -> Vec<Request>;  // what to submit
    pub fn replies(&mut self, replies: Vec<Reply>, state: &AppState);           // results (bodies, notices)
    pub fn externals(&mut self) -> Vec<External>;                               // what only Android can do
}
```

- **Frames.** `Frame` and everything in it derive `Serialize + JsonSchema`.
  - Fields: `revision`, `layout`, `top_bar`, `drawer`, `list`, `reader`, `composer`, `palette`, `settings`, `setup`,
    `banner`, `snackbar`, `back`, `theme` (only when it changed) and `wants_tick` (as `Tui::wants_tick`).
  - Strings from mail go through `app_front::text` before they enter a frame (§4.8).
- **Layout** is a function of `ViewState` and the window class (Material's size classes). It never dispatches a
  command, like a resize in the TUI.

  | Class | Width | Panes |
  |---|---|---|
  | compact | < 600 dp | One pane: the drawer while the sidebar has the focus, else the composer, else the open thread, else the list (the TUI below 80 columns) |
  | medium | 600–839 dp | The list (or the drawer while it has the focus) and the reader or composer (the TUI from 80) |
  | expanded | ≥ 840 dp | A permanent drawer (a rail after `toggle_sidebar`), the list, and the reader or composer (the TUI from 120) |

- **Navigation is the `ViewState`.**
  - Opening the drawer is `focus_pane sidebar`, as in the TUI. Opening a thread is `open_thread`.
  - Back is the `Escape` binding (`keymap::resolve`): it closes the composer, else the thread, else the search, else a
    UI-local sheet.
  - `frame.back` says whether Back is taken. When it isn't, Compose's predictive back hands it to Android and the app
    goes to the background.
- **Actions.** Every tappable thing carries an action ID from the frame's action table.
  - Kotlin returns `UiEvent::Tap{action}`.
  - The presenter resolves the ID against the table of the frame it last sent, and ignores IDs it no longer knows (like
    the TUI's `hits`).
  - Kotlin never builds a command.
- **Events** (`UiEvent`):
  - `Configure{width_dp, height_dp, dark, font_scale, locale, keyboard}` (`keyboard`: a hardware keyboard is attached)
  - `Visible{bool}`
  - `Tap`, `LongPress`, `Swipe{thread, edge}`, `Scrolled{pane, first, count}`, `Back`, `Refresh`
  - `Text{field, text}`, `Blur{field}`, `Key{chord}` (hardware keyboards)
  - `Picked{request, paths}`, `Permission{name, granted}`
  - `Notification{action, thread}`, `Shared{to, cc, subject, body, paths}`
  - `Tick`
- **Externals** (Kotlin carries them out, like `app_gui::External`):
  - `OpenUrl{url}`, after a sheet that shows the full target.
  - `PickFiles{request}`, `SaveAttachment{message, part, name, mime}`, `SaveAll{message, parts}`.
  - `KeepAlive{sending}`, the send service (§4.4).
  - `Haptic`.
- **Text fields.**
  - Kotlin owns a field's text while the IME edits it (composition, autocorrect, swipe). It sends `Text` as the text
    changes and `Blur` when the focus leaves.
  - The presenter keeps the typed buffers and submits one `update_draft` per pause (1 s, through `Tick`), field change
    or command: the rule the GUI and the TUI follow.
  - A change made elsewhere (the debug bridge today, an agent channel later) bumps the field's `generation` unless the
    field has unsaved typing. Kotlin replaces its text only when the generation changes.
- **The list** is a window of `ThreadSummary` rows around what Kotlin reports as visible (`Scrolled`).
  - The rows are computed once per `AppState.revision`, like `app_gui::list::RowCache`.
  - `LazyColumn` shows `total` items, keyed by thread ID, with placeholders outside the window.
- **Gestures.**
  - Swipe left: `archive_threads`. Swipe right: `trash_threads`.
  - A long press: `check_threads`. In checked mode the bulk bar acts on `palette::targets`.
  - Pull to refresh: `sync_now`.
  - The compose button: `create_draft`, then `open_composer`, as in the GUI.
  - The top bar's search opens the palette with *Search mail for …* first, like the desktop's search pill.
- **Reader.**
  - Messages are collapsed and expanded with `expand_messages` and `collapse_messages`.
  - HTML is drawn natively from `app_core::document`: paragraphs, headings, lists, quotes, preformatted text, data
    tables, links.
  - Plain text gets folds (`app_front::fold`). Search words are marked (`app_front::highlight`). *Links (N)* lists the
    links.
  - A tap on a link opens a sheet with its full target: *Open* (in the browser) and *Copy*. A `mailto:` link opens a
    draft.
- **Attachments out.**
  - Images and text are previewed in the app (bytes through `blob`, §4.3).
  - *Save* and *Save all* go through the Storage Access Framework.
  - There is no "open with": attacker files are not handed to other apps, as on the desktop.
  - `save_attachments` is not used: its `dir` is a path, and the system's file picker returns URIs. Saving is a
    presentation action, like the desktop's previews.
- **Theme.**
  - `app_mobile::theme` turns the active `app_theme::Theme` into tokens: roles as ARGB, the type scale, and metrics in
    dp. The theme follows the `theme`, `theme_light` and `theme_dark` settings and the system's dark mode.
  - Compose maps the tokens onto a Material 3 `ColorScheme` and a `DailTokens` composition local.
  - The fonts and the Material Symbols subset come from `crates/app-theme/assets/fonts`, so there is one copy of each.
    Icons are drawn by their `app_theme::Icon` code points.
  - `list_density` applies. `text_scale` doesn't: the system's font size does.
- **Strings.**
  - Kotlin shows no text of its own. Labels come in the frame from `app_front::i18n`, in the language from `Configure`.
  - `open` returns the few labels Android needs before the first frame (the notification channels, the push
    notification).
  - Compose mirrors layouts and runs the bidi algorithm for RTL languages.

### 4.3 The JNI surface (`app-android`)

Kotlin's `object Native` (package `net.darii.dail`, the application ID, §5):

| Call | Kotlin thread | What it does |
|---|---|---|
| `open(config, listener): String` | dail-ui | `config` = `{profile_dir, cache_dir, backend: "live" \| {"memory": fixture}, lang, version}`. On Android it sets up ndk-context and keyring's default store, then opens the profile and the session. Returns `{handle, strings}` or `{error}` |
| `event(handle, event): String` | dail-ui | One `UiEvent`: submits its requests and returns `{frame, externals}` |
| `frame(handle): String` | dail-ui | After a wake-up: takes the replies and returns `{frame, externals}` |
| `blob(handle, request): ByteArray?` | IO | An attachment part, or a decoded image scaled to the screen: its width and height (two little-endian `u32`), then RGBA. `null` if neither can be read |
| `background(handle, task): String` | IO (a job's or a service's thread) | Blocks until done or timed out. Tasks: `check` (sync and wait), `flush`, and in debug builds `exec{origin, command}` and `state` |
| `close(handle)` | dail-ui | Shuts the session down (tests, *Remove all data*) |

- A handle is a small integer that indexes a table, never a pointer. Android's arm64 heap pointers carry a tag in their
  top byte, so a pointer wouldn't survive a trip through JSON or through Kotlin.
- `Listener` has `wake()`: a new frame is ready, so post `frame` to dail-ui. It also has `alert(json)`: post a
  notification. Both are called from tokio threads, each attached to the VM once.
- **Host** (`app_android::Host`) is the JNI-free core. It holds:
  - the tokio runtime (two workers);
  - the session, opened from `ProfileDirs::at(profile_dir)` like `app-cli`'s `open_owned`: `ProfileStore`,
    `KeyringSecrets`, `NetVerifier`, `NetImap`, the full-text index and the audit log;
  - a `SessionClient`, and an `app_sync::Bridge<Purpose>` with `Origin::Gui` (`Bridge::own`);
  - `Mobile`, behind a mutex;
  - the alert watcher (§4.4).

  Tests drive the Host without JNI (§6).
- **Errors and panics.** Every call answers in JSON, `{"error": …}` on failure. A panic is caught at the boundary
  (`catch_unwind`) and becomes an error, so it never unwinds into the VM.
- **Threads.**
  - Kotlin calls `event` and `frame` on one thread ("dail-ui"), never on the main thread, and hands the decoded frames
    to Compose's state. `blob` and `background` run on IO threads.
  - Rust never blocks dail-ui on the network: `Bridge::submit` only queues, and `state()` is an `Arc` clone.
- **Origins.**
  - The app is the user's graphical front-end, in-process like the GUI, so it submits as `Origin::Gui`. There is no
    new origin, and with no IPC on Android nothing else can claim this one.
  - Background checks submit `sync_now` as `runtime`.
  - The debug bridge submits as `cli`, or as `mcp` for the agent-policy tests (§4.7).
- **Logging.**
  - `tracing` writes to logcat, `warn` and above in release builds. The layer writes to logd's socket (for example
    `tracing-logcat`) and is vetted by `cargo deny`.
  - It also writes to `<profile>/logs/android.log` (0600).
  - Never secrets.

### 4.4 Process model and background work

- **One host per process.**
  - `DailApplication` holds the handle. The first activity, job or service to need it opens it;
    `Application.onCreate` never does, because broadcasts start the process too.
  - The session stays open while the process lives. Every change is already in redb, and drafts are saved after 5 s
    idle. Closing the session would cancel scheduled sends (ARCHITECTURE §4.4).
  - Android ends the process when it likes; the next start loads the snapshot.
- **Sends.**
  - While a draft has a scheduled or running send, the presenter emits `KeepAlive{sending: true}`. Kotlin then runs a
    foreground service, *Sending…*, until `MessageSent`, `SendFailed` or `cancel_send`.
  - The service is declared `shortService|dataSync`. `startForeground` passes `shortService` from Android 14 and
    `dataSync` before, which has no time limit there.
  - The undo window (at most 60 s) plus SMTP's 120 s timeout fit in a short service's 3 minutes. So leaving the app
    inside the window still sends, as on the desktop, where the window stays open.
  - If Android kills the process anyway, the engine cancels the send at the next start (ARCHITECTURE §4.4), and the
    app posts *Not sent* once for that draft.
- **Leaving the app** (`Visible{false}`).
  - Kotlin schedules a one-off job, with network required and expedited from Android 12, that runs
    `background(flush)`.
  - The flush waits, for at most 3 minutes, until queued triage ops that aren't backing off have run, drafts are saved
    to the server and attachment saves are done. It returns at once when nothing waits.
- **Background checks** (`background_sync`, a new setting, A5):

  | Value | Mode | What runs |
  |---|---|---|
  | 0 | while open | Nothing but sends and the exit flush |
  | 1 (default) | periodic | A persisted JobScheduler job every `background_interval_mins` (15–720, default 30), with network required. `background(check)` submits `sync_now` as `runtime` and waits, at most 3 minutes, until every account's `SyncStatus.pending` is 0. Doze and app standby defer it |
  | 2 | push | A foreground service keeps the process alive, and the engine's IDLE watches do the rest (ARCHITECTURE §5.2 step 11). Its type is `specialUse` with the subtype "IMAP IDLE push e-mail", or `dataSync` before Android 14. A silent, minimised notification shows *Watching N inboxes* with *Stop*. It starts from Settings (a user action) and after a reboot (`BOOT_COMPLETED`, allowed for `specialUse`). The periodic job stays as the fallback. Settings link to the battery-optimization screen |

- **A network change** while the app is visible submits `sync_now` (as `runtime`), so a dropped Wi-Fi doesn't wait out
  the back-off.
- **Notifications** have one path.
  - While no activity is visible, the host compares each new state with the previous one through
    `app_front::alerts`, which keeps the desktop's kinds, cleaning and limits. It then calls `Listener.alert`.
  - Alerts gain the thread or draft they are about. The desktop's notifications can use that later.
  - Channels: *New mail*, *Not sent*, *Background*. On the lock screen a notification says only *New mail*, without
    sender or subject.
  - The actions *Archive* and *Mark read* go through `event(Notification…)`, as `Origin::Gui`. A tap opens the thread
    (`open_mailbox`, then `open_thread`).
  - `POST_NOTIFICATIONS` is asked for when the first notification would show. The `notifications` setting = 0 still
    turns them off.
- **New settings** (core, A5): `background_sync` (0–2, default 1) and `background_interval_mins` (15–720, default 30),
  in `config.toml` and through `set_setting`. Only the Android host reads them, as only the TUI reads `tui_colors`.

### 4.5 Storage, secrets and files

- **Profile.** It lives at `<filesDir>/profiles/default` (`ProfileDirs::at`), with the layout of ARCHITECTURE §6
  unchanged, lock included. There is no IPC socket: no other process may use the profile.
- **Backups.** `android:allowBackup="false"`, and data-extraction rules that exclude everything. The cache is mail, and
  the Keystore keys that protect the passwords can't be restored on another device.
- **Secrets.**
  - keyring 4 uses `android-native-keyring-store` as keyring-core's default store. `open` sets it up and gives
    ndk-context the `JavaVM` and the application context.
  - `KeyringSecrets` and its callers stay as they are.
  - The Keystore key needs no user authentication, because background checks run while the phone is locked (after the
    first unlock).
  - Uninstalling or *Clear storage* removes the passwords. The existing *re-enter password* fix handles that.
  - If the crate fails review (§9), a Kotlin vault goes behind `SecretStore` over JNI instead: an AES-GCM key in
    AndroidKeyStore, and the ciphertext in a private file.
- **Attachments in.**
  - The system file picker and the share sheet give content URIs. Kotlin copies each file into
    `<filesDir>/outgoing/<uuid>/<name>`, named with `app_io::mime::safe_file_name` and stopping at 25 MiB.
  - The presenter attaches that absolute path with `attach_file`, unchanged.
  - At start, the host removes the copies that no draft names.
- **Temporary files** go into `cacheDir`.

### 4.6 The Kotlin app (`android/`)

```text
android/
  settings.gradle.kts  build.gradle.kts  gradle/libs.versions.toml  gradle/verification-metadata.xml  gradlew …
  app/build.gradle.kts                 # SDK 36, minSdk 29, ABI splits, flavours live/demo, the cargo-ndk task
  app/src/main/AndroidManifest.xml
  app/src/main/kotlin/net/darii/dail/
    Native.kt  Host.kt  DailApplication.kt
    MainActivity.kt  ui/        # frame types (kotlinx.serialization) and screens: drawer, list, reader, composer, palette, settings, setup
    work/                       # SendService, PushService, CheckJob, FlushJob, BootReceiver
    notify/                     # channels, NotificationActionReceiver
    intents/                    # ShareActivity: mailto: and ACTION_SEND → a draft
  app/src/debug/kotlin/net/darii/dail/DebugBridge.kt   # the adb bridge (§4.7), debug builds only
  app/src/test/        # JVM: contract fixtures; Robolectric + Compose over the host-built libdail.so
  app/src/androidTest/ # emulator smoke tests
```

- **No rules in Kotlin.** Kotlin never sees `AppState`. It decodes frames, draws them, returns events and carries out
  externals. Its few Android decisions (which service type, when to ask for a permission) are host mechanics, not mail
  rules.
- **Frame types** are hand-written `@Serializable` classes. The contract fixtures (§6), decoded strictly (an unknown key
  fails), keep them honest. Generating them with `typeshare` is an option if they churn (§10).
- **Dependencies** are pinned in `gradle/libs.versions.toml`, the Gradle side of `[workspace.dependencies]`.
  - The app: AndroidX core, activity-compose, lifecycle, the Compose BOM (ui, foundation, material3),
    kotlinx-serialization-json.
  - Tests: JUnit, Robolectric, compose-ui-test, androidx.test.
  - Not WorkManager: JobScheduler is enough, and WorkManager brings Room along. No Google Play Services, Firebase or
    analytics.
- **The Gradle side of `cargo deny`:**
  - dependency verification: `verification-metadata.xml` holds a checksum per artifact;
  - a licence allowlist: Apache-2.0, MIT, BSD (for example with the Licensee plugin);
  - a formatter check;
  - Android Lint with warnings as errors.
- **The APK check** (`cargo xtask android apk-check`):
  - `lib/<abi>/` holds only `libdail.so`, or a prebuilt that is on an explicit allowlist with a reason;
  - every `.so` is 16 KB-aligned (`zipalign -c -P 16`);
  - a release APK is not debuggable and has no debug provider;
  - the permissions are exactly `INTERNET`, `ACCESS_NETWORK_STATE`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`,
    `FOREGROUND_SERVICE_SPECIAL_USE`, `FOREGROUND_SERVICE_DATA_SYNC` and `RECEIVE_BOOT_COMPLETED`.
- **AGENTS.md §5's rule against C**, read for Android: nothing but Rust is compiled for dail. The SDK's prebuilt tools
  (aapt2, d8, zipalign) are toolchain, like `rustc`. Prebuilt native libraries inside dependencies are refused unless
  the APK check's allowlist names them.
- **Release builds** are shrunk by R8, with keep rules for the classes JNI calls (`Listener`) and for the serialization
  classes.

### 4.7 Agents and the phone

Reviewed with the user on 2026-10-22. The question: can on-device models such as Gemma 4 use `dail mcp` on the phone?
And if not, what would an MCP server on the phone be for?

What exists:
- Gemma 4 E2B and E4B run on the device (§2). A model doesn't speak MCP: an app has to run the agent loop and call the
  tools.
- The one Android app that runs such a loop over MCP is Google AI Edge Gallery.
  - Its MCP client has been experimental since 2026-05-19: Streamable HTTP, custom auth headers, Gemma-4-E4B
    recommended.
  - Its docs give on-device models 4k–10k tokens of context, and ask to enable only the tools needed, with short
    descriptions.
  - They want a publicly routable URL (a tunnel). Whether it reaches `http://127.0.0.1` on the same phone is untested.
- dail's MCP, measured with `dail mcp --backend memory` on 2026-10-22:
  - 94 tools, an 89 KB `tools/list` (about 22k tokens) and 2.2 KB of instructions;
  - that is 2–5 times the whole on-device context before a single message is read;
  - a `list_threads` result, with its `untrusted_content`, adds kilobytes more.
- The system assistant (Gemini, whose Gemini Nano 4 is built on Gemma 4) reaches apps through AppFunctions, not MCP.
  Only privileged system apps may call them (§2).
- A desktop agent doesn't need the phone. It triages the same IMAP mailboxes through the desktop's dail, and the phone
  shows the result after its next sync. The agent's send requests are approved on the desktop.

Decision for Wave 4:
- **No agent channel in release builds.**
  - No MCP server in the app.
  - No approvals screen: nothing on the phone could create a request.
  - No *Agent requests* notification channel.
  - ADR 0009 records this as an exception to AGENTS.md §1 (channel parity). On Android, release builds have the palette
    only, until a client exists that can use a channel.
- The registry still drives everything. The palette reaches every command (the parity walk), and the host submits
  registry commands, so a channel later is one more transport over the host's `submit`.
- **The debug adb bridge** (A2; debug builds only) is a content provider that answers only the shell UID (2000).
  - `exec` submits a command as `cli`: `adb shell content call --uri content://net.darii.dail.debug --method exec --arg
    '<command JSON>'`.
  - `exec_agent` submits as `mcp`, to test the agent policy.
  - `state` and `frame` return JSON.
  - With `uiautomator dump` (the accessibility tree), `screencap` and `input`, an agent on the desktop drives and reads
    the app on an emulator, as it does the TUI under tmux (Appendix D). The instrumented tests use it too.

Later, in order of promise (§10):
1. **Cross-device approvals.** Approve the desktop agent's sends from the phone: the agent use case where the phone
   matters.
   - A request could travel with the draft's server copy in Drafts, for example as a keyword that the phone shows as a
     request. Approving on the phone sends the draft from there.
   - It needs its own design and threat review.
2. **AppFunctions** for the system assistant, with a short list of functions, once Gemini's integration opens.
3. **A compact MCP tool profile** for small models: a few tools, short descriptions, small results.
   - It helps small local models on the desktop too, such as Ollama with Gemma 4.
   - A loopback server on the phone would follow only if a mobile MCP client matures.
4. **An in-app agent** on an on-device model (the ML Kit Prompt API or LiteRT-LM). It would be weighed against ROADMAP's
   "bring your own model, nothing hard-wired", and against the rule on native code: LiteRT-LM is a prebuilt C++
   library.

### 4.8 Security (rows for ARCHITECTURE §9)

| Threat | Control |
|---|---|
| Spoofing through mail text (an RLO in a file name, control characters) | `app_front::text` on every string from mail in a frame; the TUI's test, run over frames (A3) |
| Deceptive links | A tap shows the full target before anything opens. Only `http`, `https` and `mailto`, as documents keep them |
| Tracking pixels | Remote images never load. `cid:` images show per sender (`show_images_from`), decoded by `app_io::images` within its limits |
| Another app makes dail attach a private file (`file://`, or the app's own content URI, in `ACTION_SEND` or `VIEW`) | `file://` is refused, and so are content URIs of the app's own authorities. Files are copied with a size cap. An intent only creates a draft that the user sees, never a send |
| Exported components | Only the launcher activity and the share/`mailto:` activity. Receivers are not exported, and `PendingIntent`s are immutable. Release builds have no listening socket and no server |
| The debug bridge | Debug builds only (`src/debug/`), and it answers only the shell UID. The APK check fails a release APK that has it |
| Credential leak | Keystore-wrapped secrets; nothing secret in the logs or logcat (`warn` in release). The password crosses JNI once, into `add_account`'s write-only `Secret` |
| Mail in backups | Backups are off for everything |
| Attacker files run by other apps | No "open with". Images and text are previewed in the app; other types are saved |
| The lock screen | A notification's public version shows only *New mail* |
| MITM | rustls with app-tls and webpki roots, as on the desktop. User-installed CA certificates are not trusted (a known limitation) |

### 4.9 Accessibility and input

- TalkBack names come from `app_front::a11y` (the GUI's AccessKit names).
- Touch targets are 48 dp; the system font scale applies (`sp`); so does app-theme's contrast audit; the focus order
  follows the reading order.
- Hardware keyboards (tablets, Chromebooks):
  - Compose's key events become `app_front::keymap` chords and go through `KeyState::press`. So `j`, `k`, `e`, `#`,
    `s`, `u`, `z`, `/`, `Ctrl+K` and `g i` work as on the desktop.
  - `Configure{keyboard}` says when a keyboard is attached.
  - A test checks that every bound command has a key Android delivers.

## 5. Build and toolchain

- **Tools:**
  - the Rust targets `aarch64-linux-android` and `x86_64-linux-android`, added with rustup. They stay out of
    `rust-toolchain.toml`, so desktop-only work downloads nothing more;
  - `cargo-ndk`;
  - NDK r28 or newer, pinned with `ndkVersion`;
  - JDK 17, and the Android SDK with platform 36;
  - the Gradle wrapper, with `distributionSha256Sum`.

  Versions current in 2026-10: AGP 9 (Gradle 9.1+), Kotlin 2.3, Compose BOM 2026.08. The catalog pins them when A2
  starts.
- **Gradle builds the library.** An `Exec` task runs before the native-libs merge: `cargo ndk -t arm64-v8a -t x86_64
  --platform 29 -o <build>/rustJniLibs build -p app-android [--release]`, with `-C link-arg=-Wl,-z,max-page-size=16384`.
  So `./gradlew assembleDebug`, and Android Studio, build everything.
- **xtask:**
  - `cargo xtask android check`: clippy with `-D warnings`, for both Android targets, over the crates the app links;
    from A2 also Gradle's lint, the formatter and the JVM tests.
  - `apk`: assembles the APKs.
  - `apk-check`: the checks of §4.6.
  - `test`: builds the Rust test binaries of app-core, app-io, app-tls, app-sync and app-mobile for
    `x86_64-linux-android`, pushes them to an emulator and runs them through adb.
- **Verification loop.** A gate, `android`, comes after `smoke` (`cargo xtask verify android`). It is not part of the
  default run, because it needs the SDK and the NDK. A missing tool is reported as "cannot run", never as passed
  (AGENTS.md §6).
- **CI:**
  - an `android` job (ubuntu-latest, with JDK 17, the SDK, the NDK and cargo-ndk) runs `cargo xtask verify android`;
  - an `android-emulator` job (KVM, an API 36 x86_64 image) runs `cargo xtask android test` and the instrumented smoke
    tests.
- **Release.** `release.yml` gets an `android` job:
  - a signed APK per ABI (`dail-<version>-arm64-v8a.apk`, …), each with a `.sha256`;
  - the signing key comes from repository secrets and never enters the repository. Keep a backup: with a lost key,
    users can't update;
  - the version code is derived from the workspace version and the ABI.
- **Application ID.** `net.darii.dail` (it can't change after the first release). The Kotlin package is the same, so
  the JNI symbols are `Java_net_darii_dail_Native_*`.

## 9. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| Vendors' battery managers (Samsung, Xiaomi), Doze, app standby buckets | Periodic checks come late or not at all; push is stopped | Push as an opt-in foreground service; Settings link to the battery-optimization screen; the device check measures it |
| `AppState` holds every cached envelope in memory | A large cache costs RAM on a phone, and Android kills big background processes first | Measure RSS at 10k and 100k messages (A3's scale test, A7); a smaller `initial_window` on the phone if needed; deltas later |
| `android-native-keyring-store` is young (1.0 in 2026-04), and its jni 0.21 sits next to 0.22 | Passwords fail on some devices | The live test on several devices (A1, A7); the Kotlin vault behind `SecretStore` as the fallback |
| JNI mistakes (leaked local references, threads not attached) | Crashes | Six calls only, in one place (`jni.rs`); panics caught; the device tests |
| Logic creeps into Kotlin | The front-ends' rules drift apart | Kotlin never sees `AppState`; a review rule in AGENTS.md §5; the contract tests |
| JSON frames are too slow for big mailboxes | Jank | Windowed rows, cached per revision; frames off the main thread; the scale test's budget |
| A Play review rejects `specialUse` later | No push in the Play build | Periodic is the default; the justification is written (Appendix C) |
| AGP, Compose and Kotlin churn | Builds break | The version catalog, dependency verification, deliberate upgrades |
| The undo window ends while the process is frozen | A send leaves late, or is cancelled | The keep-alive service from the moment the send is scheduled (§4.4) |

## Appendix D — adb for agents and testers

`adb shell` hands its line to a shell on the device, which parses it again, so quote JSON for that shell too.

```bash
# Install a debug build (the demo flavour runs on the memory backend with the `basic` fixture)
adb install -r android/app/build/outputs/apk/demo/debug/app-demo-x86_64-debug.apk

# Commands through the debug bridge (debug builds only): as the user (`cli`), or as an agent (`mcp`)
adb shell "content call --uri content://net.darii.dail.debug --method exec --arg '{\"cmd\":\"list_mailboxes\"}'"
adb shell "content call --uri content://net.darii.dail.debug --method exec_agent --arg '{\"cmd\":\"send_draft\",\"args\":{\"id\":\"…\"}}'"
adb shell "content call --uri content://net.darii.dail.debug --method frame"

# Read the screen: the accessibility tree (TalkBack's names) and a screenshot
adb exec-out uiautomator dump /dev/tty
adb exec-out screencap -p > screen.png

adb shell input tap 540 1200
adb shell input text 'hello'
adb shell input keyevent KEYCODE_BACK

# Logs
adb logcat -s dail

adb shell cmd jobscheduler run -f net.darii.dail <job id>            # run the periodic check now
adb shell dumpsys deviceidle force-idle                        # enter Doze now (`unforce` leaves it)
```
