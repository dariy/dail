# Plan: open the repository, and dail on iOS/iPadOS

- Status: proposal (2026-10-24). The items are ROADMAP Wave 5. ADR 0010 (item I0.1) records §2–§4.
- Decided with the user on 2026-10-24:
  1. There is no local Mac. Everything that needs macOS (Xcode, Swift, linking, the simulator, signing) runs on
     GitHub-hosted `macos-latest` runners. The agent writes the code on Linux and reads the run logs with `gh`.
  2. The repository becomes public first, so that macOS runner minutes are free (§1).
  3. The first iOS artifact is an **unsigned IPA** plus a simulator build. The user installs the IPA on a personal iPad
     by re-signing it with a free Apple ID (AltStore/SideStore or Sideloadly, re-signed every 7 days; Developer Mode
     on). Signed ad-hoc and TestFlight builds wait for a paid Apple Developer account (§6).
- Goal of the wave: a dail app that installs and runs on the user's iPad. It reads the demo mailbox and a live account
  through the same engine, registry, keymap, palette flows and agent policy as the desktop and Android, with no rules
  in Swift. The goal is not iOS feature parity with Android. That comes in a later wave (§8).
- Assumes the workspace as of `a2f87ac` (Wave 4 A7 release).

## 0. Constraints that shape every item

- **No Swift compiler on the dev machine.** Swift and Xcode errors are found only in CI. Keep Swift small, and push
  logic into Rust, which *can* be checked locally: `cargo clippy --target aarch64-apple-ios` type-checks on Linux.
  Linking needs the Apple SDK, so it happens only on the runner.
- **Feedback loop.** One push, then a 10–20 min macOS job. Batch the Swift changes, and keep the iOS jobs path-filtered
  so they don't run on unrelated pushes. A `workflow_dispatch` trigger lets you re-run them by hand.
- **AGENTS.md §5 (no C/C++ compiled).** Linking Apple system frameworks (Security, Foundation) is allowed, the way
  Windows links system DLLs. Nothing may compile C, so no `cc`. Check every new crate with `cargo deny` and
  `cargo tree -i cc --target aarch64-apple-ios`.
- **No hand-edited `.pbxproj`.** Generate the Xcode project on the runner from `ios/project.yml` (XcodeGen, installed
  by Homebrew in CI). Keep the generated `ios/Dail.xcodeproj` out of git (`.gitignore`).

## 1. Opening the repository (phase O)

Do this before any iOS work. The user flips the visibility. The agent prepares everything else.

1. **Secret scan of the whole history**, not just the tree: run `gitleaks detect --log-opts="--all"` and
   `trufflehog git file://. --only-verified`. Already checked on 2026-10-24: the tree tracks no keystore, `.env` or
   `local.properties`. If anything turns up in the history, rotate it first, then rewrite (`git filter-repo`) or
   accept it. That decision is the user's.
   *Done 2026-10-24* (gitleaks 8.30.1, trufflehog 3.99.7, all 62 commits on every ref). trufflehog found nothing,
   verified or unknown. gitleaks found 213 hits, all of them test data: Wycheproof vectors, the throwaway TLS test keys
   (`crates/app-tls/testdata/certs/README.md`) and two RFC 4231 HMAC vectors in `hash.rs`. `.gitleaks.toml` allowlists
   exactly those, and with it `gitleaks git --log-opts=--all .` reports no leaks. There is nothing to rotate or rewrite.
2. **Read every file a stranger will see:**
   - `docs/requests/*` and `docs/reviews/*`: personal notes, addresses or other names.
   - test fixtures under `crates/*/tests` and `tests/`: real mail addresses or server names beyond the user's own
     domain.
   - `AGENTS.md`, and the `Claude-Session` trailers in commit messages (they stay; they are only links).
   *Done 2026-10-24.* `docs/requests` and `docs/reviews` hold technical notes only. The fixtures used three real
   domains (`x.org`, `nullmail.io`, `quantuminstitute.ch`); they are now `.example` names. Kept: `@gmail.com`
   addresses with generic local parts (Gmail is a reference provider, and its preset matches the domain), Hostinger's
   public endpoints, and `net.darii.dail`, the user's own application ID.
3. **LICENSE.** The user chooses (for example MIT OR Apache-2.0, which is common in Rust, or GPL-3.0-or-later as
   Thunderbird-adjacent clients often use). Then:
   - add `LICENSE*` files;
   - set `license` in `[workspace.package]` and `license.workspace = true` in every crate;
   - check that `deny.toml`'s licence allowlist accepts dail's own licence;
   - check that the Android About screen still lists everything.
4. **README.md** (there is none). Include:
   - what dail is;
   - a screenshot (from the GUI's snapshot tests or a `dail gui --backend memory` capture);
   - the platforms;
   - how to build (`cargo xtask verify`);
   - where releases are;
   - a pointer to AGENTS/ARCHITECTURE/ROADMAP.

   Also add `SECURITY.md` (private vulnerability reporting through GitHub advisories) and a short `CONTRIBUTING.md`
   (the gates and the commit style from AGENTS.md §7).
5. **Workflow hardening**, in the same change:
   - `permissions: contents: read` at the top of `ci.yml` and `release.yml`. Only a release job that publishes gets
     `contents: write`.
   - Pin third-party actions to commit SHAs (`taiki-e/install-action`, `Swatinem/rust-cache`,
     `reactivecircus/android-emulator-runner`). Add a Dependabot `github-actions` entry to keep the pins fresh.
   - Never use `pull_request_target`. Keep release jobs on `workflow_dispatch` only, so that secrets never meet
     fork PR code.
6. **Repository settings** (the user, in the GitHub UI; list them in the plan's checklist):
   - Settings → Actions → General: "Require approval for all outside collaborators"; workflow permissions
     "Read repository contents".
   - Branch protection on `main`: require the CI jobs, no force-push.
   - Turn on private vulnerability reporting, secret scanning and push protection.
   - Check the Android signing secrets are *repository* secrets (not environment-less org secrets), and optionally
     move them into an environment named `release` that requires approval.
7. **Flip the visibility.** Then run `ci.yml` once to confirm that every job passes on the free runners.

## 2. Options for the iOS host

| Option | Verdict |
|---|---|
| **SwiftUI over `app-mobile` frames, through a C ABI** | **Chosen.** Android's pattern: Rust computes frames, Swift draws them and does only what iOS can (text input, VoiceOver, Keychain, files, notifications). The JSON contract and its fixtures already exist |
| egui on iOS (winit) | Same IME gap as on Android (ADR 0009 §1). Touch would need a rewrite |
| UniFFI Swift bindings | Generated Swift is acceptable (no JNA problem on iOS), but the call surface is six JSON calls. A generator adds a build step and a dependency for little gain. Revisit if the surface grows |
| WebView (Tauri) | Rejected for the same reason as on Android: hostile HTML would meet a browser engine |
| `dail tui` over SSH (Wave 1.5) | Already works today. It is no app, but it stays the fallback |

## 3. Crate layout

Today `app-android` holds both the platform-neutral host (`host.rs`, `calls.rs`, `config.rs`, `outgoing.rs`,
`error.rs`) and the Android glue (`jni.rs`, `secrets.rs`, `logging.rs`). iOS needs the first group unchanged.

- **New crate `app-host`** ← app-core, app-io, app-sync, app-mobile (and app-testkit behind `demo`, as ADR 0001/0009
  allow). It takes the platform-neutral modules out of `app-android`, as they are: `Host`, the call bodies as plain
  `fn(&str) -> String`, the config and the outgoing queue. It has the workspace lints with `forbid(unsafe_code)`.
  Its tests move with it.
- **`app-android`** ← app-host (+ app-core, app-io, app-sync as needed). Only JNI, the Keystore store and logcat. No
  behaviour change. The Android gate must stay green: this refactor lands *before* any iOS code, as its own item.
- **New crate `app-ios`** ← app-host. `crate-type = ["staticlib", "rlib"]`, `[lib] name = "dail"` (`libdail.a`).
  - `src/ffi.rs`: the six calls as `#[unsafe(no_mangle)] pub extern "C" fn dail_open/dail_event/dail_frame/dail_blob/
    dail_background/dail_close`, plus `dail_string_free` and `dail_bytes_free`.
    - UTF-8 `*const c_char` in, Rust-owned `*mut c_char` out. Swift frees what it receives with `dail_string_free`.
    - Blobs come out as `{ ptr, len }`.
    - The `Listener` callback (alerts, wake) is a C function pointer plus a `void *context`, called from runtime
      threads. Swift hops to the main actor.
  - The lint exception copies ADR 0009's: `unsafe_code = "deny"`, and only `src/ffi.rs` has `#![allow(unsafe_code)]`
    with a `// reason:` line. `tests/it/lints.rs` pins the table, like app-android's.
  - **Header:** a hand-written `include/dail.h` (eight functions). A test parses it and compares the names with the
    exported symbols in `ffi.rs`, so that no `cbindgen` dependency is needed. If cbindgen is preferred, it's a dev-tool
    run by xtask, never at build time.
  - `cfg(target_os = "ios")` parts:
    - **Secrets:** keyring-core with Apple's store. Before choosing, check what the keyring 4 family ships for iOS
      (expected: `apple-native-keyring-store`, protected data/Keychain) and that it compiles no C (it should only link
      `Security.framework` through `security-framework`). If it fails `deny`, write a tiny Swift-side Keychain bridge
      instead, reached through the callback table.
    - **Logging:** `tracing` to `os_log`. If that needs C, write to a file in the app container, which `blob` can
      export.
  - It builds and tests on Linux like app-android, so `cargo test --workspace` covers it. The iOS-only parts sit behind
    the cfg.
- **Dependency rules (AGENTS.md §2) to add:** `app-host ← app-core, app-io, app-sync, app-mobile`;
  `app-android ← … app-host`; `app-ios ← app-host` (app-testkit behind `demo`). `app-mobile` stays untouched.
- **Portability of the session on iOS**, to confirm with clippy for `aarch64-apple-ios` in I1 and with tests in the
  simulator in I3:
  - redb (mmap/file locks);
  - tantivy (mmap; check memory limits on the iPad);
  - tokio;
  - getrandom (SecRandomCopyBytes);
  - app-tls with webpki roots;
  - `ProfileLock` (flock in the app container);
  - `directories`-style paths. The host gets its profile directory from Swift (Application Support), never from env.

## 4. The Swift app (`ios/`)

```text
ios/
├── project.yml              # XcodeGen spec: app target, test target, iOS 17+, iPhone+iPad, bundle id net.darii.dail
├── Dail/                    # SwiftUI sources
│   ├── DailApp.swift        # App entry, scene, lifecycle → `background` calls
│   ├── Native.swift         # the only file touching the C ABI: strings in/out, free, callback trampoline
│   ├── Frame.swift          # Codable mirror of app_mobile::Frame (decoded strictly)
│   ├── Views/…              # draw frames: mailbox list, thread list, message, palette, compose (later)
│   └── Info.plist bits via project.yml
├── DailTests/               # XCTest: decode every contract fixture; open the demo host, take a frame
└── Frameworks/              # (gitignored) DailCore.xcframework built by xtask
```

- **Rules stay in Rust**, as in Kotlin: Swift draws frames, returns `UiEvent`s and runs host actions (`External`).
- **The contract:** reuse Android's contract fixtures (the JSON frames from the `insta` snapshots). `DailTests`
  decodes all of them strictly, so a frame change that would break Swift fails CI. Write the Codable types by hand
  from the schemas, as Kotlin's were. Add a test that compares the type list against `schemars` output.
- **Minimum for this wave:**
  - open the session (demo flavour, then live);
  - mailbox list, thread list, message view (text bodies; images off, as on the desktop);
  - mark read/star/archive, undo;
  - the command palette (parity: it reaches every command, like Android's walk);
  - account setup and settings through the palette flows.

  Leave for later: compose UI beyond the palette's flows, background fetch, notifications, iPad multi-column polish.
- **Flavours:** two schemes, `Demo` (app-ios with `demo`, memory backend) and `Live`. CI builds both. The demo IPA is
  the first thing to put on the iPad.
- **Deployment target:** iOS/iPadOS 17. It covers current iPads and keeps SwiftUI APIs modern. Revisit if the user's
  iPad runs something older: **ask for its model and iPadOS version in I0**.
- **Bundle id:** `net.darii.dail`, as on Android. A free Apple ID re-signing tool may rewrite it, which is fine.

## 5. Build and CI

- **`cargo xtask ios`**, mirroring `cargo xtask android`:
  - `check`: clippy `-D warnings` for `aarch64-apple-ios` and `aarch64-apple-ios-sim` over the crates the app links.
    This runs on Linux too, and is the local gate.
  - `xcframework` (macOS only): `cargo build --release` for `aarch64-apple-ios` and `aarch64-apple-ios-sim`, then
    `xcodebuild -create-xcframework` with `include/` as the headers, giving `ios/Frameworks/DailCore.xcframework`.
    Use `x86_64-apple-ios` only if Intel simulators are ever needed; current runners are arm64.
  - `app`: `xcodegen generate`, then `xcodebuild build-for-testing` and `test` on an iPad simulator, then
    `xcodebuild archive` with `CODE_SIGNING_ALLOWED=NO`, packed into `Payload/Dail.app`, zipped as
    `dail-<version>-unsigned.ipa`.
  - Without macOS, Xcode or the targets it reports **"cannot run"**, never a pass (AGENTS.md §6).
- **`ci.yml`, new job `ios`** on `macos-latest`:
  - path filter: `crates/**`, `ios/**`, `xtask/**`, `Cargo.*`, the workflow file;
  - rustup targets, rust-cache, `brew install xcodegen`, `cargo xtask verify ios` (= `ios check xcframework app`);
  - upload the simulator test results (`.xcresult`) on failure.
- **`release.yml`, new job `ios`:**
  - builds the unsigned IPA (Demo and Live) with `.sha256`, and uploads them as artifacts;
  - later, the signed path (§6) behind the presence of secrets, and inside the `release` environment.
- Add `ios` to AGENTS.md §6 as a non-default gate, like `android`, and to the CI description there.

## 6. Signing and installing

- **Now (free):** CI makes `dail-<v>-demo-unsigned.ipa` and `dail-<v>-unsigned.ipa`. The user:
  1. downloads the artifact (`gh run download`);
  2. re-signs and installs it with SideStore/AltStore (the AltServer/Linux pairing helpers) or Sideloadly, on their
     own Apple ID;
  3. turns on Developer Mode on the iPad.

  The limits: re-sign every 7 days, at most 3 apps, and no push entitlements (not needed yet). Write the steps into
  ARCHITECTURE §7.6 once they have worked for real. Check the current state of these tools at that time.
- **Later (paid, $99/yr), optional item I4.3:**
  - Make a distribution certificate (`.p12`) without a Mac (openssl CSR, then the developer portal) and an ad-hoc
    profile with the iPad's UDID, or an App Store profile for TestFlight.
  - Store the secrets: `DAIL_IOS_CERT_P12_BASE64`, `DAIL_IOS_CERT_PASSWORD`, `DAIL_IOS_PROFILE_BASE64`, and for
    TestFlight `DAIL_ASC_KEY_ID`, `DAIL_ASC_ISSUER_ID`, `DAIL_ASC_KEY_P8_BASE64`.
  - The job builds a temporary keychain in `$RUNNER_TEMP`, imports the certificate, runs `xcodebuild -exportArchive`
    and uploads with `xcrun altool`/`notarytool`-style App Store Connect API calls, then deletes the keychain
    (`if: always()`), as the Android job deletes its keystore.

## 8. Out of scope for Wave 5 (a later "Wave 6 — iOS parity")

Full compose UI with attachments through the Files picker, background app refresh and BGProcessingTask, notifications
(local; no APNs server), iPad multi-column and Stage Manager polish, hardware-keyboard shortcuts (the keymap through
`UIKeyCommand`), Share-sheet and Files integration, the App Store, Mac Catalyst. Also out: an agent channel on iOS,
for the same reasons as on Android (ADR 0009, plan §4.7).

## 9. Risks

| Risk | Mitigation |
|---|---|
| A dependency compiles C for iOS (a `cc` build script) | Run `cargo tree -i cc --target aarch64-apple-ios` in I1, before any Swift. Replace it, or put it behind a cfg |
| The keyring store for iOS is missing or compiles C | Fallback: a Swift Keychain bridge through the callback table (§3) |
| Swift churn through slow CI loops | A small Swift surface, strict fixtures tested in Rust first, and Swift changes batched per push |
| tantivy/redb memory or mmap limits on the iPad | Measure in the simulator in I3. The index can be turned off (`search` falls back to the server) |
| Free-account sideloading breaks (Apple policy changes) | The simulator build keeps CI meaningful. The paid route (§6) is the fallback |
| Opening the repo leaks something old in the history | §1.1 scan before the flip; rotate first |
