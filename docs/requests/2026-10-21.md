## UX-1 — Persisted view preferences

`ViewState` is not saved, so collapsed folders, focus, sidebar state and filters reset on every start.

**Proposal.** A `[view]` table in `config.toml` (decided 2026-10-21: `config.toml` for now; a separate file can come
later if the table grows) with `sidebar_collapsed`, `collapsed`, `focus_mailbox`, `list_filter` and
the GUI's pane widths. There is a new `PersistDelta::View` that View commands emit (`ConfigStore` writes it,
`RedbStore` ignores it). It is not part of undo history, which matches the `View` kind. This keeps the "View mutates only
`ViewState`" rule. The only new thing is that some of that state is saved.

## UX-2 — Folder tree instead of a flat list

**Today.** `listing::mailboxes()` returns a flat list. The sidebar shows only the last path segment, so
`Work/Clients/Acme` and `Personal/Acme` both read "Acme".

**Proposal.**
- A pure projection `app_front::mailbox::tree(state, account) -> Vec<FolderNode>`. Each node has `{ key: FolderKey { account,
  path }, label, depth, mailbox: Option<MailboxId>, children, unread, unread_below }`. It is built from `path.split(delimiter)`.
- Special-use folders (Inbox, Sent, Drafts, …) stay on top, flat, in role order, as they are today. User folders follow
  as a tree, sorted case-insensitively.
- Missing parents (`\Noselect`, or never listed) become *synthetic* nodes (`mailbox: None`). They can be expanded but not
  opened.
- Gmail: `[Gmail]/…` children are all role folders. If a synthetic node is left with no children, it is hidden. Nested
  labels (`a/b`) nest naturally. This is data, not an `if gmail` branch: "hide empty synthetic nodes" applies to every
  provider.
- A collapsed parent shows the sum of unread mail below it (`unread_below`) as a faint badge.
- MCP/CLI: `list_mailboxes` output gets `parent` (path or null) and `depth`, so agents see the same hierarchy (additive JSON
  fields, no break).
- TUI: the same projection, indented two spaces per level, with `▸`/`▾` markers.

**Tests.** Projection unit tests in `app-front` (`/` and `.` delimiters, missing parents, Gmail layout, sort order,
unread rollup). GUI snapshot via the existing demo.

## UX-3 — Collapsible folders and accounts

**Proposal.**
- `ViewState.collapsed: BTreeSet<FolderKey>`. A key with an empty `path` collapses the whole account.
- New `View` commands (agent access: allowed): `collapse_folders { keys }` and `expand_folders { keys }`, where empty
  `keys` means all. Both are idempotent, so they are safer for agents than a toggle. The GUI picks one by looking at the state.
- GUI: a chevron on parent rows and account captions. Click on the chevron toggles, click on the name opens. Keys: `←`/`→`
  (or `h`/`l` in the vim preset) on the focused sidebar row. These are new `default_keys` entries in the spec.
- The open mailbox is never hidden: if a collapse would hide it, its account row shows the open marker.
- Persisted via UX-1.

## UX-4 — Focus on one mailbox

**Interpretation.** The user works one folder ("Support", "Invoices") without distraction from the rest.

**Proposal.**
- `ViewState.focus_mailbox: Option<MailboxId>`. View commands `focus_mailbox { id }` and `clear_focus {}` (allowed for agents).
- While focused:
  - the sidebar shows only that mailbox (with its subtree from UX-2) and a "Show all folders" chip;
  - `open_mailbox` on another mailbox clears the focus (explicit navigation wins);
  - the unified inbox is hidden;
  - desktop notifications (`app-gui/desktop.rs`) fire only for new mail in that mailbox;
  - the list title shows a "Focus" badge.
- A variant `focus_mailbox { account }` focuses a whole account. It hides the other accounts, for people who keep work
  and private mail in one profile.
- Palette: "Focus this mailbox", "Exit focus". Keymap: `g f` (vim) / `Ctrl+Shift+F`.
- Persisted via UX-1, so a focused session restarts focused.

## UX-5 — Mark as read after a delay

**Today.** Opening a thread never marks it read (`BODY.PEEK`, no `\Seen`). The user must press `Shift+I` or click.

**Proposal.**
- Setting `mark_read_after_ms` (u64). `0` means off, which is the current behaviour. Any other value means "mark the
  open thread's unread messages read once it has been open this long". Range: `0` or `250..=60_000`. **Default: `2000`**
  (decided 2026-10-21). A missing key takes the default, so existing profiles get it too.
- **Where the timer lives: in `app-front`, not the engine.** Core Law: `ingest` (a `Tick`) never records undo history,
  but this must be an ordinary, undoable `mark_read`. So the front-end owns the timer:
  `app_front::autoread::AutoRead { thread, opened_ms }` with `fn poll(&mut self, state, now_ms) -> Option<Command>`. It
  returns `mark_read { messages: <unread messages of the open thread> }` once, when the delay has passed and
  `view.thread` is still the same thread. The GUI calls it each frame and uses `ctx.request_repaint_after(remaining)`.
  The TUI uses its event-loop timeout. Both submit the command with `Origin::User`.
- Consequences:
  - Agents opening threads over MCP never mark mail read by accident. Their reads stay side-effect free.
  - Undo (`z`) restores unread.
  - Leaving the thread before the delay cancels the timer.
  - An explicit `mark_unread` while the thread is open disarms the timer until another thread opens, so it does not
    fight the user.
- Options: mark only messages that are expanded (default), or the whole thread. Also, do not fire while the window is in
  the background (the GUI knows `viewport().focused`). The default is to pause while unfocused.
- **Configurable from the UI** (decided): a "Mark as read" control in the GUI settings with "Never / Immediately
  (0.25 s) / After 2 s / After 5 s / Custom…" (Custom takes seconds, one decimal). The TUI settings screen has the same
  choices. Both submit `set_setting { key: "mark_read_after_ms", value }`, so the palette, CLI and MCP get it for free.

**Tests.** `app-front` unit tests with fake `now_ms`: fires once, cancels on navigation, disarmed by `mark_unread`, no
command when there is nothing unread.

## UX-6 — Automatic periodic sync with the servers

**Today.** INBOX gets IDLE push plus polling every `poll_secs` (120 s). Every other folder (Sent, Archive, user
folders, the open folder) is synced only by `sync_now`, and `open_mailbox` does not fetch.

**Proposal.** All of this stays in the engine's existing `Tick` → `poll()` path (`engine/sync.rs:294`), so it is
deterministic and replayable:
1. **Refresh on open.** `open_mailbox` emits `FetchEnvelopes` for the mailbox when its last fetch is older than
   `stale_secs` (default 60) and no fetch is in flight. There is precedent: `open_thread` already emits `FetchBody` and
   tracks `status.bodies_in_flight`. This needs `Mailbox.last_fetch_ms` (ingested from `EnvelopesFetched` with `now_ms`).
2. **Poll the open mailbox too.** Each poll fetches INBOX plus `view.mailbox` (if it is not INBOX).
3. **Full round.** Setting `full_sync_secs` (default 900; `0` = off). When it is due, the poll does a whole
   `ListMailboxes` → fetch-all round for each idle account, like `sync_now`, so new folders, Sent and Archive stay fresh.
   Backfill keeps running as today.
4. **Back-off when offline.** If an account's last round failed with a network error, the next poll of that account waits
   `min(poll_secs × 2^n, 15 min)`. The `ops::retry_delay_ms` pattern applies. Any success resets it.
5. **Status.** `status.next_poll_ms` already exists. The status bar shows "Synced 2 min ago · next in 1 min", and a
   palette entry "Sync now" is already there.
6. **Later (separate item):** IDLE on more than INBOX (one connection per watched folder, capped, setting
   `watch_mailboxes`). QRESYNC is already on the roadmap.

**Tests.** Replay fixture `tests/replay/periodic_sync.jsonl`: ticks at fixed times produce the expected effects; a stale
`open_mailbox` fetches, a fresh one does not; back-off doubles and resets.

## UX-7 — List-pane toolbar (second pane)

**Today.** Bulk actions appear only after a thread is checked. There is no visible "select all", "mark all read",
refresh, or filter.

**Proposal.** A thin, always-visible toolbar under the list title (GUI) and a one-line action hint (TUI):
- **Tri-state select-all checkbox.** None → `check_threads { ids: [] }` (exists: checks every listed thread). All →
  `uncheck_threads { ids: [] }`. Some → shows "–".
- **Mark all as read.**
  - Phase 1: `mark_read { ids: <all listed threads> }` (cached window; undoable; no new command).
  - Phase 2: new `Mutation` `mark_mailbox_read { id }` that also covers uncached server mail: local seen on every cached
    message, plus a `PendingOp` with `UID STORE 1:* +FLAGS (\Seen)`. Its undo restores only the cached messages it changed;
    the receipt says so (`uncached_affected: true`). Agent access: allowed (no data leaves the machine). With more than
    N unread messages, the GUI asks for a confirmation.
- **Refresh.** A refresh button: `fetch` of the open mailbox (the UX-6 refresh-on-open path), with a spinner while it is
  pending.
- **Quick filters** (`View`): `set_list_filter { unread?: bool, starred?: bool, attachments?: bool }`. They are stored in
  `ViewState.filter` and applied by the list projection (`Rows::of` in `list.rs`, `AppState.revision` caching stays
  valid when the filter is part of the cache key). Chips: "Unread", "Starred", "📎".
- **Sort:** newest first (today) or oldest first, `set_list_sort`. Optional, low priority.
- **Context-sensitive extras:** "Empty Trash" / "Empty Junk" in those folders, an `expunge`-style `Destructive` command
  that needs `confirm: true` (MCP `destructiveHint`).
- The current bulk bar stays and replaces the toolbar's right side while threads are checked.

## UX-8 — Pinned and hidden folders
- Settings `pinned_mailboxes` and `hidden_mailboxes`. Commands `pin_mailbox` / `unpin_mailbox` / `hide_mailbox` /
  `show_mailbox` (Mutation on settings, undoable, allowed for agents).
- Pinned folders appear in a "Favourites" section above the accounts. Hidden ones disappear from the tree but stay in
  search, in "Move to…" and in a "Show hidden" toggle.

## UX-9 — Sync state per account in the sidebar
The account caption shows a small spinner while syncing, a warning dot with the error on hover (auth / TLS / network,
from the existing error UX), and "offline" while ops are waiting. The data is already in `status.sync` and `outbox`.

## UX-10 — Row hover actions and context menu (GUI)
On hover, a row shows archive / trash / star / read-toggle icons on the right. Right-click opens a menu with the same
actions plus "Move to…" (palette flow) and "Focus this mailbox". All of them push existing commands. This needs AccessKit
labels for each icon.

## UX-11 — Drag threads onto sidebar folders (GUI)
egui's in-app drag-and-drop (`dnd_set_drag_payload`) moves the checked threads (or the row) onto a sidebar node:
`move_threads { ids, to }`, undoable as today. A hovered synthetic node from UX-2 does not accept drops. Dragging *out*
to the OS stays blocked (winit), as the roadmap notes.

## UX-12 — Auto-advance after triage
Setting `after_triage`: `next` (default, Gmail-like) / `previous` / `list`. After archive/trash/move of the open thread,
`app-front` opens the neighbour or returns to the list. This is shared by the GUI and the TUI, and it is plain View commands.

## UX-13 — Date group headers and row density
- The list groups rows under "Today / Yesterday / This week / Earlier this month / <Month Year>". It is computed in
  `app-front::format` from `now_ms`, and the virtualized `show_rows` needs fixed-height header rows.
- Setting `list_density`: comfortable (52 px, today) or compact (one line, ~28 px).

## UX-14 — Folder management
`create_folder { account, path }`, `rename_folder { id, path }` (Mutation, undo = rename back), and `delete_folder { id,
confirm }` (Destructive). Runtime: IMAP `CREATE` / `RENAME` / `DELETE` in `app-sync` and in the testkit fake. Agent
access: allowed for create and rename; delete is Destructive (confirm). The tree (UX-2) gets "New subfolder…" and
"Rename…" in its context menu.

## SEC-1 — Symmetric encryption of the local data (research)

### What is stored, and how today
| Path | Content | Sensitivity |
|------|---------|-------------|
| `state.redb` | envelopes (subjects, addresses, flags), threads, drafts (full text), outbox, approvals | high |
| `blobs/**.eml` | full raw messages and attachments, named by **plaintext SHA-256** | highest |
| `index/` (tantivy) | inverted index of body words | high (it rebuilds the text) |
| `backups/*/state.redb`, `config.toml` | copies of the above | high |
| `logs/replay-*.jsonl` | commands and events; bodies and passwords redacted, headers kept | medium |
| `config.toml` | accounts (addresses, servers), settings; secrets are only `SecretRef` | low–medium |
| temp files | PDF preview copies, "Open original" HTML | high, short-lived |

Passwords are already only in the OS keyring. Everything else is plaintext, protected only by file modes (0700/0600 on
Unix) and whatever disk encryption the OS has.

### Threat model: what at-rest encryption does and does not buy
It **protects against**:
- a lost or stolen laptop or disk without full-disk encryption;
- a profile directory copied by backup or sync tools (Dropbox/OneDrive/Time-Machine-style), by support bundles, or by a
  careless `tar` of `$HOME`;
- another local user, or a forensic image of the disk;
- the plaintext-hash filenames, which today let anyone with a known message confirm that you have it.

It **does not protect against**:
- malware running as the same user. On Linux the Secret Service collection is unlocked at login, and any process of the
  user can ask it for the key. On Windows, Credential Manager / DPAPI is per user, not per application. Only the
  passphrase mode (below; decided to build it) raises the bar, and only while dail is locked;
- the running process (`AppState` holds the plaintext in RAM), swap, or hibernation files;
- the servers, which have all the mail anyway.

**Recommendation:** full-disk encryption (LUKS / BitLocker) stays the first line of defence and is
documented as such. SEC-1 is defence in depth for the cases listed above.

### Design options considered
1. **Encrypted database engine (SQLCipher-style).** Excluded: it needs C (`libsqlite3-sys`/OpenSSL, banned by
   `deny.toml`). redb has no built-in encryption.
2. **Encrypted container or filesystem** (gocryptfs, VeraCrypt, a FUSE layer). Not portable to Windows, an external
   dependency, and not in dail's control. Mention it as a user-side option only.
3. **Application-level, per-record and per-file AEAD in `app-io` (recommended).** Values are sealed before they reach
   redb or the disk. It is pure Rust, works the same on Linux and Windows, and changes neither the `Store` trait nor
   `app-core`.

### Recommended design (option 3)
**Primitives** (pure Rust, RustCrypto; all pass the no-C rule):
- **XChaCha20-Poly1305** (`chacha20poly1305` crate; RustCrypto AEADs were audited by NCC Group): 192-bit random nonces,
  so random nonces are safe at any realistic volume and no counter state is needed. It is fast in software on every CPU
  (it does not depend on AES-NI), and it is the same cipher family dail already uses for TLS.
  - Alternative: reuse `app-tls`'s ChaCha20-Poly1305. It has no audit, it is TLS-scoped, it has no XChaCha, and it would
    add a new `app-io ← app-tls` edge. Not recommended.
- **HKDF-SHA256** (`hkdf`) to derive per-purpose subkeys from one master key: `records`, `blobs`, `blob-names`, `index`,
  `logs`.
- **HMAC-SHA256** (`hmac`, with `sha2` already in the tree) for blob names: `blob_id = HMAC(k_names, plaintext)`. This
  keeps deduplication and stops anyone without the key from confirming a known file.
- **Argon2id** (`argon2`) only for the optional passphrase mode (m = 64 MiB, t = 3, p = 1, tunable and stored with the
  key file).
- `zeroize` (already in the tree) on every key buffer. Nonces come from `getrandom` (already in the tree). Randomness in
  `app-io` is fine: it is the I/O crate, and `app-core` stays sans-IO.
- Rejected: the `age` crate as the file format. It is solid but heavier, its key model (X25519 recipients, scrypt) does
  not fit the keyring, and the random-access chunking it would need for the index is not exposed.

**Key hierarchy.**
```
master key MK (32 random bytes, generated once)
  ├─ wrapped in <profile>/store.key  {version, kdf params, salt, key_id, wrapped MK (XChaCha20-Poly1305)}
  │    wrapping key KEK = keyring item "dail/<profile>/store-kek"          (default: no prompt)
  │                 or = Argon2id(passphrase, salt)                         (passphrase "lock" mode)
  └─ HKDF(MK, info = "dail/v1/<purpose>") → k_records, k_blobs, k_names, k_index, k_logs
```
Because MK is wrapped, a passphrase change or a keyring move re-wraps 32 bytes and does not re-encrypt the data.
`store.key` also keeps old key IDs after a rotation, so older backups still open.

**Formats.**
- Record (redb value): `"D1" | key_id u32 | nonce 24 | ciphertext+tag`. The AAD is `table name | record key |
  schema_version`, so records cannot be swapped between rows or tables without detection.
- Blob: the same header on the whole file (messages are read whole today). Name = HMAC id. Very large attachments
  could later use 64 KiB chunks (STREAM construction) for streaming.
- Logs: each JSONL line is sealed separately (`{"enc":"<base64>"}`), so appends stay cheap and a torn last line only
  loses that line. `dail replay` decrypts.
- `config.toml`: stays plaintext by default (it holds no secrets, and the user edits it by hand). An option seals only
  the `[[account]]` addresses and servers.
- `meta` table: `encryption = {alg, key_id, check}`, where `check` is a sealed known value. With it, a wrong key gives a
  clear "wrong passphrase / missing key" error, not "broken cache".

**Full-text index (tantivy) is the hard part.** tantivy reads segment files with random access through its
`Directory` trait. Options:
- (a) a custom `EncryptedDirectory`: segments are written once and never changed, so they can be sealed in 64 KiB chunks
  that each decrypt independently; `meta.json` / `managed.json` go through `atomic_write`, sealed whole. mmap is lost, so
  reads are a little slower. This is the recommended end state.
- (b) interim: while encryption is on, keep the index in RAM only and rebuild it in the background from blobs at start.
  For 100k messages this takes minutes, so only as a stop-gap.
- (c) interim: turn local full-text search off and use server `SEARCH` (which exists). This is simplest; ship it first
  (opt-in only) and document it. Because encryption becomes the default, (a) is required before that switch.

**Temp files.** PDF preview and "Open original" copies go to a profile-private `tmp/` (0700), are deleted when the
reader closes them and on exit, and are swept at start. They must stay plaintext because another program reads them.

**Commands** (registry; all `AgentAccess::UserOnly` because they handle key material, per AGENTS.md §4):
- `enable_store_encryption { passphrase?: Secret, confirm: true }` (Destructive kind: it rewrites the store).
- `disable_store_encryption { confirm: true }`.
- `rotate_store_key { confirm: true }`.
- `change_store_passphrase { old?: Secret, new?: Secret }`.
- `lock {}` / `unlock { passphrase: Secret }` for passphrase mode: lock drops MK from memory and clears the cached
  bodies and the view.
- `export_recovery_key {}`: shows MK once as a base32 code to write down; the GUI only, never printed to logs.
- `status.encryption` (state, key_id, locked) is shown in the settings and by `dail doctor`.

**Where it lives (dependency rules unchanged).**
- `app-core`: only the commands, their validation, and an effect `ReencryptStore { mode }` / `LockStore`. No crypto.
- `app-io`: a `Sealer` (keys + seal/open). `RedbStore`, `BlobDir`, `AuditLog` writer and the backup code take
  `Option<&Sealer>`. Migration `1 → 2` adds `meta.encryption`. Re-encryption runs in one pass: a new redb file plus new
  blob names, then the envelopes' `body: fetched{blob}` references are rewritten in the same write transaction, then an
  atomic rename. A crash midway leaves the old store intact.
- `app-sync`: the keyring KEK (it already owns `keyring`), the passphrase prompt plumbing, and running the effect.
- New workspace deps: `chacha20poly1305`, `hkdf`, `hmac`, `argon2` (all RustCrypto, pure Rust). This needs an
  **ADR 0008 "At-rest encryption"** (new dependency class + key policy).

**Failure and recovery.**
- Missing keyring item or a wrong passphrase: dail opens with an empty cache and a clear banner. Mail is fetched again
  from the servers (the cache *is* a cache). Exceptions are **local-only drafts and unsent outbox items**. The banner
  names them, the encrypted store is set aside (like `state.redb.broken-*`) instead of being deleted, and the recovery
  key can restore it.
- Backups stay encrypted under their key ID, and rotation keeps old IDs in `store.key`.

**Cost.** XChaCha20-Poly1305 in software runs at hundreds of MB/s or more, far below the cost of the JSON parse of
100k envelopes at load. Verify with the existing `scale` tests (`--release --ignored`). The expected overhead is a few
percent at start-up and negligible per frame.

**Leaks that remain (accepted, documented).** Record counts and sizes, blob sizes, file modification times, and the
redb key layout (random u128 IDs, no content).

**On by default** (decided 2026-10-21).
- New profiles: the profile wizard (GUI, TUI, `dail account add`) generates MK and stores the KEK in the keyring before
  the first byte of mail is written. The wizard offers "Also protect with a passphrase" as an opt-in step.
- Existing profiles: on the first start of the release that turns the default on, dail makes a backup, then encrypts
  the store in place (the same one-pass rewrite as `enable_store_encryption`) and shows a one-time notice.
- No usable keyring (a headless Linux box without Secret Service, e.g. the TUI over SSH): dail does not fall back to
  plaintext silently. It asks for a passphrase (passphrase mode). The user can still opt out with
  `disable_store_encryption { confirm: true }`, and `dail doctor` then reports "local data not encrypted".
- `--backend memory` and test profiles are unaffected: nothing is written to disk.
- Search must not regress: the default flips only once phase 4 (encrypted tantivy index) is done. Until then the
  phases ship behind the opt-in `enable_store_encryption`.

**Phases.**
1. ADR 0008 + `Sealer` + encrypted redb values, blobs with HMAC names, and the keyring KEK. Index off (option c). Temp
   file hygiene.
2. Logs and backups sealed. `rotate_store_key`, `export_recovery_key`, `dail doctor` support.
3. Passphrase mode with lock/unlock (GUI prompt at start, TUI prompt, `dail` CLI reads from the tty only).
4. `EncryptedDirectory` for tantivy (option a).
5. Turn the default on: new profiles encrypted from the wizard, existing ones migrated on first start (see above).

**Tests.** Round trip per format; tampering (bit flip, swapped record keys, swapped blobs) is rejected; a wrong key gives
the "locked" error, not a corrupt-cache path; migration on and off of a fixture profile keeps state identical; a crash
injected midway leaves the old store openable; a property test that no plaintext subject or body bytes appear in
`state.redb`/`blobs/` after enabling (a grep-style scan); a secret-hygiene test that MK never appears in logs, receipts
or `Debug`.

## Decisions (2026-10-21)
1. Mark as read after a delay: default 2 s, configurable from the GUI and TUI settings.
2. View preferences: a `[view]` table in `config.toml` for now.
3. Passphrase mode: build it (SEC-1 phase 3).
4. Encryption at rest: on by default for new profiles, existing profiles migrated (SEC-1 phase 5).
5. The proposals are numbered in the order they should be built.
